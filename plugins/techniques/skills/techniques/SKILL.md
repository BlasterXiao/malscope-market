# 技术点提取与记录

把本次分析过的样本用到的技术一个个拎出来，写成一份 HTML 详细记录。

## 硬性约束

- **证据只来自本会话的查询结果。** 地址、API、字符串、常量必须在本会话里由 *sql 插件查出来过。证据不够时，先用已连接的 *sql 插件补查；补不到就标“待核实”，不要编。
- **ATT&CK 编号必须核对过。** 优先用本技能 `library/` 里已核对的编号。新编号要打开 `https://attack.mitre.org/techniques/<编号>/` 核对名称（只访问 ATT&CK 公开页面，不发送任何样本信息）；无法联网时在编号后标“（未核对）”。
- 不执行、不调试样本。
- 记录只写到本地 `./output/<样本名>/techniques.html`，不写进插件仓库。

## 第 1 步：列出候选技术点

从本次分析结果里找，按 ATT&CK 战术分类：

| 分类 | 常见线索 |
|------|----------|
| 执行 / 注入 | `VirtualAllocEx` + `WriteProcessMemory` + `CreateRemoteThread`、APC、傀儡进程 |
| 持久化 | Run 键、计划任务、服务创建、启动目录 |
| 防御规避 | API 动态解析 / 哈希、字符串加密、反调试、反虚拟机、白加黑侧载 |
| 发现 | 主机名、用户名、进程列表、网络配置收集 |
| 通信 / C2 | 自定义协议、HTTP(S)、DNS 隧道、域前置、代理链 |
| 收集与外传 | 截屏、键盘记录、文件打包、分块外传 |

列出候选后给用户看一眼清单（名称 + 一句话依据），用户确认或增删后再写详细内容。

## 第 2 步：查技术点库

本技能目录下的 `library/` 是通用技术点库，`library/README.md` 有索引和条目格式。格式要求每条写够深：不只是一句话原理，还要有按数据流编号的分步拆解、和一个读者能自己动手跑一遍的实验，让没见过这个技术的人也能照着看懂、照着试。

- 库里有的技术点：沿用它的分步拆解、动手实验和 ATT&CK 编号，样本证据和实现细节另起一节写，不要去改库里的通用内容。
- 库里没有的：按 `library/README.md` 的格式（含"分步拆解""图示""动手实验"等节）新写一条草稿，保存到 `./output/library-drafts/<slug>.md`，最后提醒用户把草稿复制进仓库的 `plugins/techniques/skills/techniques/library/` 再提交。草稿里不能出现任何样本专属信息（地址、哈希、域名、IP）。
- 写"动手实验"时只演示机制本身（编码、系统调用效果、协议字段），不要给出可直接用于攻击的完整工具；目标只用本地文件、`example.com` 这类无害对象。

## 第 3 步：每个技术点写一张卡片

卡片面向两种读者：复核这次分析的人，和不熟悉这个技术、想顺着学一遍的人。所以除了证据，还要能看懂"为什么"和"怎么一步步发生的"，不能只有流程图没有解释。

| 部分 | 要求 |
|------|------|
| 名称 / 分类 | 中文名 + 常用英文名，分类见第 1 步 |
| ATT&CK | 编号 + 官方英文名，可多个 |
| 攻击者面对的问题 | 库里有条目就直接引用其表述；没有就按 1 到 3 句自己写：不用这个技术会被什么限制卡住，给一个具体场景 |
| 核心思路 | 1 到 3 句：这个技术具体绕开了哪条限制、走哪条路；配一张「思路图」(交互图)，把被阻断的直连路径和实际绕行路径画在一起 |
| 分步拆解 | 按数据/控制流顺序编号，每步写清楚谁发起、传了什么、对方怎么处理；库里有条目的，这里对齐通用步骤编号，只补本样本在每一步的具体做法。模板里用带编号圆点的时间线渲染 |
| 交互图 / 流程图 | 填 `data-diagram` 的 JSON，渲染器自动画，见下方「图示规范」。通信/多方往返用**交互图**(sequence)，控制流/分支判断用**流程图**(flow)；合适就都留，不合适的那张整块删掉 |
| 样本证据 | 表格：证据描述 / 地址或位置 / 来源查询（写用到的插件命令，如 `/idasql:xrefs`）/ **对应步骤**（这条证据对应分步拆解里的第几步，模板已留此列） |
| 本样本的实现细节 | 和库里通用描述不同的地方：编码方式、密钥、记录类型、分段长度等 |
| 例子 | 两半：①「通用演示」从库条目「动手实验」复制(机制本身、无害输入)；②「本样本里这一步长这样」从本会话查询截取的伪代码或解密出的字符串 |
| 检测要点 | 网络侧、主机侧、样本侧三栏各写能写的；样本侧可以交给 `yara` 插件 |
| 延伸学习 | 库里有条目时，链接 `library/<slug>.md` 并提示"动手实验"小节可以自己跑一遍 |

### 图示规范

图不再手画 SVG 坐标，改成在模板的 `<script type="application/json" data-diagram="...">` 里填**声明式数据**，页面底部的渲染器(无依赖、不联网)自动排版。两类：

- **交互图** `data-diagram="sequence"`：`actors` 是参与方(竖泳道)，`messages` 每条一个箭头，字段 `from`/`to`(actors 下标)、`text`(动作)、`step`(编号，对齐分步拆解)；`blocked: true` 的消息渲染成红色虚线加叉，用来画"想走但被策略拦住的直连"。`from===to` 画成自环(本地处理)。
- **流程图** `data-diagram="flow"`：`nodes` 字段 `id`/`text`/`type`(`start`/`end` 圆角黄框、`process` 方框、`decision` 菱形)，`edges` 字段 `from`/`to`/`text`(可选，如"是"/"否"/"循环")；回边(指回上层)自动走右侧虚线。
- 顶部「技术链总览」用一张 flow 把本样本所有技术点按执行顺序串起来。

硬规则：

- **三处编号必须对齐**：图里箭头的 `step` ↔ 分步拆解的编号 ↔ 样本证据表「对应步骤」列。
- **图里每个节点/箭头都要能落到证据**，落不到的标「待核实」，不凭空画。
- 每张图配**一行「怎么看这张图」**的说明(模板里的 `.cap`)。
- **一张图只说明一个机制**，不把无关组件堆进去。
- 文案尽量短(节点/消息文字控制在十来个字)，渲染器按等宽字估宽，太长会把图撑宽。

## 第 4 步：生成 HTML

1. 读取本技能目录下的 `record.html` 模板。渲染器已内置在模板底部，不用改它、也不用联网。
2. 填写页头：样本名、分析日期、使用的 *sql 插件、技术点数量。
3. 填写“技术链总览”：先填那张 flow(把技术点按执行顺序串起来)，再填下面的总览表，每个技术点一行。
4. `<!-- CARD:START -->` 到 `<!-- CARD:END -->` 之间是一张卡片的模板，每个技术点复制一份并填写。把每个 `data-diagram` JSON 里的 `{{...}}` 换成真实数据，用不到的那类图(交互图/流程图二选一时)整块 `<div class="block">` 删掉，最后删掉模板注释。
5. 写到 `./output/<样本名>/techniques.html`。`<样本名>` 用用户给的简称，不用哈希。
6. 在对话里只给出文件路径和技术点清单（名称 + ATT&CK 编号），不要在对话里贴完整 IOC。

## 第 5 步：登记技术关联索引

这一步让"哪个组织的哪个家族用过哪个技术"能跨样本、跨会话查询，不用每次都翻回旧报告。

1. 找索引位置：读 `./output/techniques-index-path.json` 里的 `path` 字段。没有这个文件就问用户索引放在哪，或提议参照 `plugins/techniques/skills/techniques/usage-index-template/README.md` 新建一个（复制 `usage-index-template/` 到样本工作区，和"家族类型-命令控制表"同级最自然），得到路径后写进 `./output/techniques-index-path.json`（`{"path": "..."}`），下次直接读。
2. 对本次写进 techniques.html 的每个技术点，在索引的 `data/techniques.js` 里确认已登记（没有就照 `data/_template-technique.js` 加一行），再到 `data/usage/<org>/<slug>.js` 里追加一条 `FT2.addUsage({...})`（文件不存在就新建并去 `data/manifest.js` 登记）。字段只写：技术 id、组织、家族/样本简称、日期、一句话证据、指向这份 techniques.html 的路径——不写地址、哈希、域名、IP。
3. 新建或改过的 usage 文件只追加、不改写已有记录。
4. 对话里只提示索引已更新到哪个路径，不贴索引里的历史记录内容。

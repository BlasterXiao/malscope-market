# DNS 隧道 / DNS Tunneling

- 分类：通信 / C2
- ATT&CK：
  - T1071.004 Application Layer Protocol: DNS（核对日期 2026-10-12）
  - T1572 Protocol Tunneling（核对日期 2026-10-12）
- 关联技术：被阻断的直连场景常与域前置一类"借合法通道走私有数据"的技术并列讨论；库里暂未收录域前置条目，新增时互相加 `[[dns-tunnel]]` 链接。

## 攻击者面对的问题

受害主机在企业网络里，出站防火墙通常按白名单放行：80/443 给代理服务器，其它端口基本全锁死。直连任意 IP 的任意端口会被策略拦截，连不上自己的 C2。但几乎所有网络都要用域名上网，所以 53 端口的 DNS 查询总是放行的——这是唯一一条默认双向可用、又不经过应用层代理检查内容的通道。

## 核心思路

不直接连 C2，而是向内网 DNS 服务器发查询。内网 DNS 服务器看到查询的域名不在自己权威范围内，会按 DNS 的正常工作方式帮忙递归到权威服务器——而这个权威服务器恰好是攻击者自己注册、自己运维的。数据被编码进查询的子域名部分，指令被编码进应答记录里，双方的"内容"借着 DNS 协议本身的字段走私，协议本身没有被破坏，所以防火墙和大多数内容过滤器看不出异常。

## 分步拆解

1. **攻击者注册一个域名**（如 `tunnel.example`），把它的权威 DNS 服务器指向自己控制的主机 C。受害网络里的 DNS 解析器完全不知道这件事，这一步在样本运行之前就已经完成。
2. **受害主机 A 上的样本**要外传一段数据（如主机名、一个文件分片），先把这段字节编码成域名能接受的字符集——通常是 Base32（只含大小写不敏感的字母和数字 2-7，域名天生不区分大小写，用它不会因为大小写归一化丢信息）。
3. **编码结果按 63 字节一段切开**（DNS 单个标签的硬限制），每段中间插入 `.`，拼到 `tunnel.example` 前面，例如 `K5SWY3DPEB3W64TM.tunnel.example`。
4. **A 发起对这个完整域名的查询**（常见请求 TXT 或 A 记录），目标是本机配置的 DNS 服务器 B（内网递归解析器）。这一步和打开一个正常网页触发的 DNS 查询在网络层面没有区别。
5. **B 发现自己不是 `tunnel.example` 的权威**，按 DNS 协议正常行为，逐级递归（或转发给上游）直到找到权威服务器 C，把查询转过去。
6. **C 收到查询，解析出子域名里编码的数据**（上行数据到此完成接收），**在应答记录里塞进要下发的指令**（同样编码过，常见放进 TXT 记录的字符串字段，因为 TXT 天生就是"任意文本"，不像 A 记录只能塞一个 IPv4）。
7. **应答沿原路径返回**：C → （可能经过的中间递归层）→ B → A。A 的解析库把应答交给样本，样本解码 TXT 内容拿到指令。
8. A 和 C 之间**始终没有一次直接的 TCP/UDP 连接**——每一次数据交换都是"A 查询、B 转发、C 应答"这套标准 DNS 流程的一次往返，这正是防火墙按端口策略拦不住它的原因：策略看到的只是"主机在查 DNS"。

## 动手实验

下面两步分别演示"编码/分段"和"DNS 协议本身能带多少数据"，都不发起任何真实的隧道通信。

**① 看编码和分段怎么把一段数据变成合法域名**（纯本地字符串操作，不联网）：

```python
import base64

def to_dns_labels(data: bytes, suffix: str = "tunnel.example") -> str:
    b32 = base64.b32encode(data).decode().rstrip("=").lower()
    labels = [b32[i:i+63] for i in range(0, len(b32), 63)]
    return ".".join(labels) + "." + suffix

def from_dns_labels(domain: str, suffix: str = "tunnel.example") -> bytes:
    sub = domain[: -len(suffix) - 1]
    b32 = sub.replace(".", "").upper()
    pad = "=" * (-len(b32) % 8)
    return base64.b32decode(b32 + pad)

q = to_dns_labels(b"hostname=VICTIM01;user=alice")
print(q)                       # 编码后的查询域名
print(from_dns_labels(q))      # 还原回原始字节，应得到原始输入
```

预期输出：第一行是一串形如 `mzxw6...tunnel.example` 的域名（你的具体字符会不同，但结构一致）；第二行是 `b'hostname=VICTIM01;user=alice'`，和输入完全一致。这两行让你亲眼看到"任意字节 → 合法域名字符集 → 还原"这一步是怎么做到无损的。

**② 看一次真实的 TXT 查询能带多少、什么样的数据**（对公共、无害的域名发起一次合法查询，不针对任何目标）：

```bash
dig TXT google.com +short
```

预期输出：若干行带引号的文本记录（Google 会返回它的 SPF 记录等）。重点不是内容本身，而是观察到 **TXT 记录就是任意长度的自由文本**——这正是第 6 步里 C2 把指令塞进应答的原因：换成 A 记录只能塞一个看起来像 IP 的 4 字节数值，远不如 TXT 灵活。

## 常见实现

- 系统 API：`DnsQuery_A` / `DnsQuery_W` / `DnsQueryEx`（dnsapi.dll），或退而求其次用 `getaddrinfo` / `gethostbyname`（这两个只能拿到 A/AAAA 记录，塞不了太多下行数据，多见于轻量级信标而非真正的双向隧道）。
- 自建报文：`socket` + `sendto` / `recvfrom` 直连 UDP 53 端口，自己拼 DNS 报文头（跳过系统解析库，连查询类型、TTL 这些字段都自己控制，常见于更成熟的隧道工具如 iodine、dnscat2）。
- 记录类型：TXT（类型值 16，`0x10`）最常见；也有 A、AAAA、CNAME（类型值 5）、NULL（类型值 10）、MX。
- 编码：Base32（域名大小写不敏感，天然适配）、Base64 的 URL-safe 变体、纯十六进制（效率最低但实现最简单）。
- 长度限制：单个标签最多 63 字节，完整域名最多 253 个字符，所以数据按 63 字节左右分段，一次请求能带的数据量很有限——这也是隧道普遍"慢"的根本原因。
- 会话管理：子域名里常带序号、会话 ID、校验字段，防止 DNS 的缓存机制和递归路径上的乱序把分片打乱。

## 在样本里怎么找

- 查 `DnsQuery_*`、`DnsQueryEx`、`sendto`、`recvfrom` 的交叉引用，看调用者是谁、调用频率如何。
- 搜 Base32 字母表常量 `ABCDEFGHIJKLMNOPQRSTUVWXYZ234567` 或 Base64 字母表，这类查表式编码常把字母表写成一个连续的字符串常量。
- 搜常量：53 / `0x35`（端口）、16 / `0x10`（TXT 记录类型值）、63 / `0x3F`（标签长度上限，常出现在分段循环的比较指令里）。
- 看拼接域名的函数：循环里按固定长度切分、插入 `.`、拼接固定后缀——这个函数形态很固定，适合作为 YARA 特征。
- 看应答解析：取 TXT 记录内容后紧跟解码和命令分发的代码，通常在同一个函数或紧邻的下一个函数里。

## 检测要点

- 网络侧：同一域名下出现大量一次性、高随机性的子域名；子域名长度长、字符熵高；TXT 查询相对 A/AAAA 的比例明显偏高；单主机 DNS 查询频率和单次应答数据量异常。
- 主机侧：非浏览器、非系统服务的进程频繁调用 `DnsQuery` 系 API；进程绕过系统解析器，直接向 53 端口发 UDP 包。
- 样本侧：第 2、3 步对应的编码函数和分段拼接函数的指令序列，以及固定的域名后缀构造逻辑，可交给 `yara` 插件写规则。
